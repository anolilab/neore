# BROWSER EXTENSION — AGENT NOTES

The rules for working in `apps/browser-extension/`. The protocol and the reasoning are in this folder's `README.md`.

## SIGN-IN

- Both builds (Chrome, Firefox) sign in through the app grant only: `identity.launchWebAuthFlow` → `/extension/auth/exchange` → grant token in `storage.local` → `/extension/auth/token` for the bearer (`src/lib/extension-grant.ts`). Never add a cookie path back: the server must tell the extension's sends from the web app's.
- Every request to our origins sends no cookie: `credentials: "omit"` on our fetches, and the Lunora client gets a `fetch` that forces it (`src/lib/lunora-client.ts`), since it asks for `"include"` on its own. The backend strips the cookie off extension-origin requests anyway (`backend/src/extension-cookie.ts`).
- No host permission for the app origin: the extension only opens it in the sign-in window.
- A 401 from `/extension/auth/token` drops the grant (revoked or expired); sign-out revokes it server side, then forgets it even if offline.
- A sign-out (`endSession`, `src/lib/session.ts`) holds new tokens (a count, so one sign-out ending early never lifts another's hold: `releaseAccessTokens`) and stops the refresh loop; the bearer, and the offline queue clearing it drops, stays until the grant is marked signed out (`neore.signedOutGrant`). If storage fails to read the grant or write the mark, nothing changed and the session comes back (tokens resume, the loop restarts) and Settings shows the failure. The mark is checked and written under the grant lock, so an older sign-out never overwrites a newer grant's. `readGrant` hides a marked grant, so the panel signs out at once and a failed removal never signs back in, here or in a later panel; Settings is gone by then, so the sign-in page shows that failure (`useSignOutUnfinished`), and the next panel to load removes the leftover (`finishPendingSignOut`, once per panel: every `useSession` shares one storage watch; one whose storage read fails runs again on the next good read). The warning is read from storage, never kept per panel: it shows in every panel only while a failure mark (`neore.signOutFailed`, written when the revoke fails or times out or storage keeps the grant) names the stored marked grant and no removal runs in that panel, never for a sign-out still running elsewhere, and clears on a removal or a new sign-in. A sign-in drops the mark; one it fails to drop names an older key and hides nothing. A storage read that fails after a change keeps the session shown, and the watch reads again with capped backoff until one succeeds (a mark written during the outage fires no new change); only the first read counts a failure as signed out. The revoke is bounded (`REVOKE_TIMEOUT_MS`); out of time counts as a failed revoke. Never report a rejected sign-out as done. It acts on the grant Settings shows (`grantKey`), leaving a newer one unrevoked, and one sign-out runs per grant. A session started meanwhile (`suspend`'s generation check) is left alone.
- A Chrome install updated from the cookie build is told once to connect (`migrateFromCookieSession` on `runtime.onInstalled`, `neore.reconnectNeeded`), only when the old build's Lunora read cache holds something (`hasCookieBuildReads`): that build queried only when signed in. Keep the migration mark (`neore.authMigration`) so it runs once per install.
- A Chrome build signs in only when the backend lists `https://<id>.chromiumapp.org/` in `TRUSTED_EXTENSION_REDIRECT_URIS`. That one list also holds the desktop and mobile callbacks, and a value replaces it whole: add the Chrome URI to what is set, and list the Firefox URI when it was unset.
- Live queries: the socket signs in with a ticket minted for the bearer (`wireLiveSocket`, `@neore/client-runtime`); no cookie rides it.
- Every bearer goes to `lunora.setAuthToken(token, sub)` with the token's own `sub` (`src/lib/auth-token-sync.ts`): without a subject a refresh reads as another user and the offline queue is dropped, and another account's token kept under the old subject holds the queue and its cached reads until a session read names the user. `createAuthTokenSync` clears the bearer only on sign-out or another account; a new grant for the same user swaps it.
- The bearer cache and anything written after a round trip are keyed to the grant: a refresh or revoke that answers after another sign-in never touches the newer grant.
