# Triggers

Triggers let you automate AI agent execution without manually starting a conversation. When a trigger fires, it creates a new thread and runs the AI autonomously with Deep Work mode (up to 25 iterations). Results appear in your thread list like any other conversation.

## Quick Start

1. Open `/dashboard/settings/chat/triggers`
2. Click **New Trigger**
3. Choose a trigger type (Schedule, Webhook or Event)
4. Configure the trigger settings and optionally set a system prompt
5. Click **Create Trigger**, then enable it with the toggle

## Trigger Types

### Schedule

Run the AI on a recurring cron schedule — for example, daily at 8 AM or every Monday morning.

**Configuration:**
- **Cron expression** — standard 5-field cron format (minute, hour, day-of-month, month, day-of-week)
- **Timezone** — the timezone the schedule runs in (e.g. `America/New_York`)

**Examples:**

| Cron expression | Schedule |
|---|---|
| `0 8 * * *` | Every day at 8:00 AM |
| `0 9 * * 1` | Every Monday at 9:00 AM |
| `30 * * * *` | Every hour at 30 minutes past (triggers run at most hourly) |
| `0 0 1 * *` | First day of every month at midnight |

**How it works:** A background job polls every minute and checks if any enabled schedule triggers are due to fire. When one matches, a new thread is created and the agent runs your configured prompt.

A schedule must run at most hourly, and it must fire at least once in the next 28 years. Saving or enabling one that breaks either rule is refused. A schedule that was saved before the rule, or that stops matching, is switched off the next time it comes due, and the reason appears in its last error. It does not run.

### Webhook

Receive HTTP POST requests from external services (Stripe, GitHub, Zapier, etc.) and run the AI with the payload as context.

**Configuration:**
- When you create a webhook trigger, a unique **webhook URL** and **signing secret** are generated automatically
- Copy the URL and register it with the external service
- The signing secret is used to verify that incoming requests are authentic

**Webhook URL format:**
```
{LUNORA_URL}/triggers/webhook/{triggerId}
```

**Security:**
- Every request must be signed, and a trigger accepts only the headers of its own signature scheme. A request carrying the headers of another scheme is rejected, even when its own signature is valid
- **Neore (timestamped)**, the default: send `X-Neore-Timestamp` (Unix seconds) and `X-Signature-256: sha256=<hex>`, the HMAC-SHA256 of `<timestamp>.<raw body>` keyed with the secret. Requests more than 5 minutes off are rejected, and each signature is accepted once
- **GitHub-style (`X-Hub-Signature-256`)**: `sha256=<hex>`, the HMAC-SHA256 of the raw body keyed with the secret. It carries no timestamp, so a captured request can be replayed once the 15-minute duplicate window has passed
- **GitLab secret token (`X-Gitlab-Token`)**: see [Provider presets](#provider-presets)
- The scheme is chosen when the trigger is created, together with its secret, and cannot be changed afterwards
- Requests without a valid signature are rejected

**Payload handling:**
- The webhook body is passed to the AI as context
- You can define a **payload template** to transform or filter the incoming data before it reaches the AI

#### Provider presets

Instead of writing payload filters by hand, a webhook trigger can start from a provider and one of its events. Pick the provider under **Source** and the event under **Event**; Neore sets the payload filters and the signature scheme for you, and only that provider's own deliveries for that event run.

| Provider | Events | Signature |
|---|---|---|
| GitHub | Pull request opened, pull request merged, review requested on a pull request, issue assigned | `X-Hub-Signature-256` (GitHub-style) |
| GitLab | Merge request opened, merge request merged | `X-Gitlab-Token` |

A preset is a shortcut and nothing more: the trigger stores the resulting filters and scheme, exactly as a hand-written trigger does. Events whose payload cannot be told apart from a neighbouring event by its body alone are not offered.

Set the secret shown when you create the trigger as the **secret** of the provider's webhook (for GitLab, the **Secret token** field), and the trigger's URL as the target.

##### GitLab secret token

GitLab does not sign the request body. It sends the secret you configured, as plain text, in the `X-Gitlab-Token` header, and sends no timestamp. Neore compares it in constant time, but it is a **bearer token**: whoever holds the secret can send any request to the trigger.

Every GitLab delivery also carries an `X-Gitlab-Event-UUID` header. A delivery without one is refused with `401`. Neore remembers each accepted delivery, by that identifier and the body, for as long as the trigger exists. A delivery that repeats one it already accepted, however long ago, is answered `200` with `{"duplicate": true}` and does not run again, so a captured request cannot be sent again. Deliveries that differ in either the identifier or the body both run. A delivery that did not run (it missed the trigger's filters, or was refused for the daily limit or an unavailable model) is not remembered, so GitLab's retry of it can still run. The identifier is not signed, so this does not stop someone who holds the secret, who can send any request under a new identifier. Treat the secret like a password, and rotate it by creating a new trigger if it leaks. Deleting the trigger deletes these records.

### Event

An event trigger watches something and runs your agent only when it happens. The watching costs nothing: the condition is checked every few minutes without asking a model, and the agent runs once, when the condition comes true. Pick what to watch:

| Watch | Fires when | Keeps watching |
| --- | --- | --- |
| **A page changes** | The page's text changes. Add a CSS-style selector (`#price`, `.stock`, `main`) to watch one part of the page, and a phrase to fire only when the text starts to contain it. | Yes, after a cooldown |
| **A moment arrives** | The time you picked passes. | No, it runs once |
| **A thread gets a reply** | A message lands in a thread you can read, from a sub-agent, a model or another person. Your own messages do not count. | Yes, after a cooldown |

A few details:

- **The first check only records a baseline.** A page that already looks a certain way does not fire the moment you switch the trigger on; a phrase that was already on the page does not count as arriving.
- **A page is checked at most every 5 minutes** (15 by default) and must be a public `http` or `https` address. Addresses that point at private or internal networks are refused. Only the page's visible text is compared, so changing scripts, ids or markup do not fire it. Only the first 1 MiB of a page is read: a longer page is compared as cut, so a change past that point is not seen.
- **After it fires, a page or thread watcher waits** for the cooldown you set (an hour by default) before it can fire again.
- **A model's answer to your own message counts as a reply.** Only your own messages are ignored, so a thread you are chatting in fires on each answer; the cooldown is what keeps that to one run per wait.
- **You can have 10 event triggers switched on at a time.**
- **A watcher that cannot check three times in a row because of something you can fix switches itself off and tells you.** An address the server will not fetch, a page that is not text, a page that answers `404` or another client error, a selector that matches nothing and a thread you can no longer read all count. Fix the cause and switch it back on; it starts again from a fresh baseline. A timeout, a network error, a `5xx` answer or a rate limit (`408`, `425`, `429`) does not count: the watcher stays on and waits longer after each one, up to six hours, until the page answers again.
- **The run says what fired.** Its first message names the event ("The page changed: https://example.com/pricing") and quotes a short excerpt as data. Your input template says what to do about it.

## Creating a Trigger

1. Open `/dashboard/settings/chat/triggers`
2. Click **New Trigger**
3. Fill in the details:
   - **Name** — a descriptive name for the trigger
   - **Description** (optional) — what the trigger does
   - **Type** — Schedule or Webhook
4. Configure type-specific settings:
   - For Schedule: cron expression and timezone
   - For Webhook: the URL and secret are generated automatically
5. Optionally configure the agent:
   - **System prompt** — custom instructions for the AI when this trigger fires
   - **Input template** — the initial message sent to the AI (for schedules)
   - **Model** — override the default model
   - **Search mode** — set the search mode for tool calls
6. Click **Create Trigger**
7. Enable the trigger with the toggle switch

:::note
Triggers start disabled. You must explicitly enable them after creation.
:::

## How Execution Works

When a trigger fires:

1. A new thread is created, tagged with the trigger's metadata
2. The AI runs autonomously using Deep Work mode (up to 25 iterations)
3. The agent can use all available tools — web search, code execution, document creation, etc.
4. Memory extraction runs automatically after the AI finishes
5. The completed thread appears in your thread list

Each execution is logged with:
- Start and end timestamps
- Success or failure status
- Error messages (if any)

## Managing Triggers

The **Triggers** settings page (`/dashboard/settings/chat/triggers`) shows all
your triggers with their current state.

:::note
This page is not yet linked from the settings sidebar — navigate to the URL
directly.
:::

**For each trigger you can:**
- Toggle it on or off at any time
- View execution count and last triggered timestamp
- See the next scheduled run time (for schedule triggers)
- View the last error message if an execution failed
- Delete the trigger and its execution history

## Common Use Cases

**Daily briefing**
Create a schedule trigger that runs every morning and asks the AI to research and summarize the latest news in your industry.

**Webhook-driven reports**
Connect a Stripe webhook to generate a financial summary whenever a payment is processed.

**Automated monitoring**
Set up a schedule trigger to check a website or API endpoint at regular intervals and alert you to changes.

**Content generation**
Schedule the AI to draft a weekly newsletter or social media posts on a recurring basis.

## Troubleshooting

**Issue:** Trigger doesn't fire on schedule
- **Solution:** Verify the trigger is enabled (toggle is on)
- **Solution:** Double-check the cron expression — use a cron validator to confirm it matches your intended schedule
- **Solution:** Verify the timezone is correct

**Issue:** Webhook returns 401 or signature validation fails
- **Solution:** Ensure the signing secret in the external service matches the one shown in Neore
- **Solution:** For GitHub webhooks, set the secret in the webhook settings and use the GitHub provider preset (or the GitHub-style signature) — GitHub's `sha256=hex` format is supported
- **Solution:** For GitLab webhooks, enter the secret as the **Secret token** and use the GitLab provider preset (or the GitLab secret token signature)
- **Solution:** Verify the external service sends only the headers of the trigger's signature scheme — a request that also carries another scheme's header (for example `X-Gitlab-Token` on a GitHub-style trigger) is rejected

**Issue:** Trigger fires but the AI response is empty or unhelpful
- **Solution:** Add a detailed system prompt to guide the AI's behavior
- **Solution:** Include an input template that provides context for the task
- **Solution:** Enable Deep Work mode settings if the task requires multiple steps

**Issue:** Too many threads being created
- **Solution:** Adjust the cron schedule to run less frequently
- **Solution:** Disable the trigger temporarily while you refine the configuration
