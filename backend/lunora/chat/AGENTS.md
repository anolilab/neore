# CHAT — AGENT NOTES

The rules for working in `backend/lunora/chat/`. The detail and reasoning are in
[docs/agents/backend-chat.md](../../../docs/agents/backend-chat.md).

## INVARIANTS

- **Edge streaming** — the agent loop (`chat/execute.ts:runStreamingAgent`) runs on the JOBS QUEUE, not the scheduler; it claims its stream once (`claimStreamRun`) and writes `persistentChunks`, which the gateway polls (`/chat/chunks`) and relays as NDJSON.
- Stream token is HMAC `{streamId}:{userId}:{threadId}:{expiresAt}:{hmac}`, 30 min TTL.
- Interrupted runs: register (`registerResumableRun`), beat once a minute (`beatRun`, never faster) and mark tool calls (`markToolRuns`); the `watchRun` watchdog resumes a run with a beat > 3 min old via a `pauseCause: "interrupted"` pause claimed by `claimRunResume`.
- A resume derives `from`, rows and step count from SAVED rows (`settleSavedRows`), never the dead run's memory; anything unfinished (trailing tool call, delivered steer, open tool mark) fails visibly. Max 3 resumes per reply.
- A tool safe to repeat (`lib/repeatable-tools.ts`) is checked but never counted in `toolsInFlight`, so a death inside it resumes and the model calls it again; one unsafe tool open beside it still fails. Unsafe by default: built-ins only by name in `BUILTIN_TOOLS_SAFE_TO_REPEAT` (read-only and nothing else), server tools only with `readOnlyHint: true` and no destructive/open-world hint, device tools never.
- Opt-out is `userSettings.resumeInterruptedRuns === false` (absent = on). Approval continuations, group turns and stateless runs register nothing.
- **Pinned MCP tools** — an approved MCP call runs only if its tool's fingerprint (`lib/mcp-tool-fingerprint.ts`, saved in the snapshot as `mcpToolFingerprints`) still matches; changed, gone or unverifiable → answered as DENIED with the reason, never run. So is one whose runtime name now stands for another server's tool (`mcpToolOrigins`, a hash of server identity, endpoint, transport and tool name: names are given in listing order, so a bot's selection or a disabled server can shift them). The pin is for that one call, not for grants.
- **Resend of a send** — `/chat/start`'s optional `clientMessageId` is a `chat-start` claim (`chat/start-claim.ts`) holding the request's fingerprint, taken before the charge; the save checks it and records the ids in its own transaction with NO nested mutation (`createThreadWithInitialMessage`, `saveStartPrompt`, via `lib/save-prompt.ts`), and so do the goal (`startGoal`) and the stream (`createStreamWithMessage`, which inserts the row itself).
- A resend of a finished send answers `duplicate: true` with the first ids and a fresh stream token; another send under the id is 422 `CLIENT_MESSAGE_ID_REUSED`; an unfinished one within `CHAT_START_LEASE_MS` is 409 `CHAT_START_IN_PROGRESS`. A goal refused after the save is final for the id (`recordStartRefused`). Title and category jobs a try skipped are recovered once, keyed by the prompt, never paid twice: details in the reference.
- After the lease, a send with nothing saved is taken over from scratch; a text turn saved without a stream is resumed: stream and run only (and the goal its first try recorded, never a second), on the model its prompt was saved with. Its stream and goal end only goals whose start prompt was saved before its own (`comparePromptPositions`: creation time, then thread order, then id), and a goal it would start beside a later prompt's is not started; no second save or charge, under a new fence and a renewed expiry. Writes after the save check the fence (`assertStartStreamable`). The claim lives on the thread owner's shard, by design. Never save a claimed send outside those two mutations.
- **Rate-limit pause** — pause only on the gateway's `rateLimit: { status, retryAt }` field, never on message text; a bare 429 without it still fails.
- Paused streams stay `pending|streaming` with `persistentStreams.pause`; the resume is the SAME `runStreamingAgent` job with `resume: <pause id>`, claimed by `claimRunResume` (redelivery, "Retry now", stale jobs no-op) and streaming from `pause.from`.
- **Usage-limit settings** (`lib/usage-limit-settings.ts`, read by `readUsageLimitPreferences` on the person's shard, absent or a failed read = resume on, no snooze) — `resumeAfterUsageLimit: false` queues NO resume: the pause is `awaitsPerson`, and `retryPausedRunsNow` resumes it at once once its reset has passed (no overdue grace). `snoozeUntilUsageLimitReset: true` snoozes the owner's chat to the reset, only when the provider reported one, only for the owner's own run, and never shortens a later snooze. The pause's rules are unchanged.
- Caps: pause ≤ 10 min, one per step, 3 per run; steer/stateless/group/approval-continuation runs fail instead. Never wait inside an action or queue invocation. Countdown is `aria-hidden`, with a polite status region.
- **Browser automation** — `browserTool` uses the Browser Rendering worker (`@neore/service-sdk/browser-renderer`), gated on the `SERVICE_BROWSER_RENDERER` binding (`isServiceBound`); no Browserbase path.
- **Purchase clicks** (`lib/purchase-gate.ts`, `browserTool.needsApproval`) — a click whose target reads as a purchase asks in every mode, auto and grants included. In `ask` mode every browser call asks, and a click's target is read first and kept for the approved click (`askAfterLook` in `applyToolPermissions`, `askDecision`). Otherwise the target's rendered text (`visibleOnly`, not raw `textContent`) is read with the same selector before the click; a truncated read, or one with no text or name, asks. A look that returns an error (a missing element, a refusal) asks nothing: the click is refused when it runs. The read is `approvalLook`, so it never ends a person's hand-back lease. An approved click (`approvedToolCallIds` over `execute`'s messages) is checked by the renderer against the target its decision read recorded (`purchaseLooks` on the session, `expectTarget`): a changed element is refused. Keep the gate on the tool's own answer, never in the permission map.
- The SSRF guard `validateDomain` stays in `tools/utilities.ts` so the security suite tests the real function.
- **Human checks** (`browser/human-check.ts`, run by `tools/browser.ts`) — detection reads only the renderer's title, URL and short page text, never a model; a check is waited out once (`HUMAN_CHECK_WAIT_MS`), then asked about once per site per reply (insert-if-absent on the unique `browserHumanChecks` key; `run` = `ToolCtx.replyKey`, the reply's first stream; a group turn's `turn.replyKey`, a headless run's own key saved in its snapshot; else the prompt, then the thread). The wait (and `wait_for_person`'s, below) is one of the two bounded waits in an action: between two renderer calls (no hold kept), ended by Stop (`waitUnlessStopped`). "Clear" needs a successful look carrying the signal the check was found by; after a hand back, a whole-page text read. For a check found in the text (`inText` on the row), a text read too long for the detector (or truncated) is unknown, never clear nor asked about. URL markers read only the parsed path and query keys. An ask from `needs_person` (`reported` on the row) shows no marker, so after its hand back the agent is told to check, never that it looks clear. A hand back still showing a check on a site asked to clear one recently (`HUMAN_CHECK_HAND_BACK_WINDOW_MS`, `detected` only) gets no wait, no second card and no new row (it would restart the window). A navigate, or a click, type or scroll that changed the URL (not only its fragment), gets one whole-page text read (`navigated`); if that read fails, the agent is told the new page was not checked. The ladder's own reads skip the user's `browser/action` limit (`ladderLook`, set only by `tools/browser.ts`) and are capped at `HUMAN_CHECK_LOOK_BUDGET` per tool call. Generic phrases ("press and hold") count only beside a challenge word. Whatever the ladder returns after a hand back keeps that result's note first and its `success: false` (`keepHandBack`). An open ask keeps no browser alive (that would be paid idle time): it closes on the renderer's idle reap, the card then says so, and the agent's ask note tells it a retry navigates on a new browser. The card's screenshot is only of the asked site, and the card offers Take control only while the thread's browser is the one asked about (`humanCheck.browserId`: the browser the action that showed the check ran on, never a later query) and on its site. The agent never solves or bypasses one.
- **Human-check answers** (`browser/human-check-card.ts`) — the card answers an ask once (`done`/`declined`, `resolution` on the row, refused while impersonating, write access like Take control); the result carries `humanCheck.checkId` only for an ask that call recorded. A decline is told to the agent for the rest of that reply (the run's own row): a navigate to the site is refused, and any result on it carries the decline, a clear page too; a later reply may ask again. `wait_for_person` polls the ask it began on (the run's latest) for at most `HUMAN_CHECK_ANSWER_WAIT_MS`, once per ask (`waitedAt`), never in a headless run, and Stop ends it.
- **Ask-user** (`chat/tools/ask-user.ts`) — keep `needsApproval: true` hard-coded; answer only via `chat_ask_user.answerAskUser` (`respondToToolApproval` must refuse it); headless runs drop it (`BUILTIN_TOOLS_NEEDING_A_PERSON`).
- Ask-user takes ONE form per call: `question` (+`choices`) or `questions` (≤ `ASK_USER_MAX_QUESTIONS`). The reply must match the form (`answer` text vs `answers` list); `resolveQuestionAnswers` validates picks against the call's own choices inside the claim, and the stored output carries `answer` OR `answers`, never both.
- Ask-user constants stay in `ask-user-constants.ts`; `agent-run.ts` must not import the tool module.
- **Low-risk quick check** (`chat/lib/low-risk-approval.ts`, `low-risk-check.ts`) — opt-in (`aiUserPreferences.autoApproveLowRisk`, absent = off, set only by `setAutoApproveLowRisk`); order: taint, budget (`chat/toolAutoApprove`), one utility-model call; anything but a clean `lowRisk: true` prompts.
- Eligibility is decided BEFORE the model and the verdict never widens it: MCP/connector tools only, from a trusted server only (`aiUserPreferences.lowRiskTrustedServers`, name AND url or connector slug, written only by `setLowRiskTrustedServer`, max 50; a call naming no server is refused).
- Also required: only the DEFAULT `ask` (no user override), no destructive/open-world annotation, not headless, not an API-key run, `isDeviceEligibleThread` (owner alone).
- The tool name must START with a `READ_VERBS` verb (allowlist), and `OUTWARD_WORDS` over the tool's own name is a second gate; a new write verb prompts by default.
- Never after context the person did not write: taint = `computeTaint(messages)` + `messagesCarryAttachedText` (build attached text only through `documentTextPart`) + `untrustedContext` (knowledge, memories, project context, ANY skill text via `injectsSkillText`). Any enabled skill disables the check. A guest note the owner sent on is saved as `guestTextPart`: `computeTaint` reads it as untrusted and `mayExtractMemory` never mines it.
- A continuation reads `toolRunConfig.untrustedContext` from its snapshot (absent = tainted). Setting and thread sharing are re-read at every call in `consumeLowRiskCheck`.
- Stamp the approval via `stampSavedToolCalls` (`providerOptions.neore.autoApproval`) on every run end; a failed stamp never changes the run's outcome. Log `chat.low_risk_check` per decision.
- **Side questions** (`chat/aside.ts`) — read-only snapshot, writes nothing (answer lives in `useAsideStore`); refuse an unreachable custom endpoint, never reroute to a hosted model; a host-run thread sends the QUESTION ALONE.
- Aside billing: `chargeDailyLimit` "Text" right before the model call; own-model asides book `forwardReplyUsage` under `aside:<entryId>` on the thread owner's shard, which reads the project there; the action reads no usage, and a failed booking is logged, never raised (`usage/AGENTS.md`). `addAsideToThread` writes ONE row and is refused while a reply runs. `parseCustomModelId` returns `null` for a non-custom id.
- **A bot's tool selection** (`bots/tool-selectors.ts`, shared with web; `bots.toolSelection`, absent = every tool) — `allow` absent = every tool, present = only those (empty = none); `exclude` always wins. Selectors: a built-in by name, `<key>:tool`, `<key>:*`, the key being the server's stable identity (`mcp=<url>`, `connector=<slug>`, `device=<id>`), never its display name (refused on save; the form resolves a typed name). Matched whole, never split. Found by `readRunToolSelection` (`bots/run-tool-selection.ts`): the named bot, the thread's, or a sub-agent chain's lead, with NO owner check (a collaborator's turn is narrowed too), returned with the bot's `ownerId`; an unreadable thread gives no tools. An exclusion naming an `mcp=` key no saved server has (an edited address) strips every user server in the owner's own run; in a collaborator's run (`ownerServerKeys`, read with the bot) only a collaborator server whose address the owner also saved.
- It only removes: `buildAgentTools` applies it to every run before connector access and permissions, and skips servers it could keep nothing from; the MCP-app proxy reads it with the thread on the owner's shard (`threadModeForApp`) and refuses a call naming no chat when the caller has any bot with a selection. All fail closed (the proxy reads saved servers with `getSavedMcpServerUrls`, which throws, never `getMCPServersQuery`, which answers `[]` on failure). A new path that assembles a run's tools must apply it. Changing it is refused while impersonating, a save naming an unknown built-in is refused (`listBuiltInTools`), and a save sent with `expectedToolSelection` that no longer matches the stored one is `CONFLICT`.
- **Time-boxed tool allows** — stored in `aiUserPreferences.toolPermissionGrants`, never an `auto` override, and kept OUT of `auth/fields.ts` so no client input sets one. "Always allow" is refused for `ALWAYS_ALLOW_REFUSED_BUILTINS` (`lib/tool-permissions.ts`: paid or sending built-ins); their hour and today allows still work, except the person-only ones (merge, saved-login sign-in), which take no timed allow at all (`isGrantableKey`).
- `resolveToolPermission` lifts only `ask` → `auto`, before the API-key clamp; `off` wins; headless runs never read grants; `device:` keys and `builtin:askUser` never take one. The MCP-app proxy (`lib/mcp-apps.ts`) ignores grants.
- Granted tools get `needsApproval: () => Date.now() >= expiresAt`; "today" ends at local midnight (`userSettings.timezone`, UTC default); prune via `pruneExpiredToolPermissionGrants`.
- **Auto-continue ("Deep Work")** — raises `maxSteps` from 5 to 25; all triggers use it by default.
- **Step-cap wrap-up** (`lib/cap-wrap-up.ts`, used by `execute.ts`) — a run that ends on its cap with a tool step gets ONE more call with `tools: {}` and `toolChoice: "none"`, saved under the reply. A stop before it skips it, and a stop during it aborts the call (polled every `STOP_POLL_MS`, there is no pipe); also skipped for an approval pause, a loop the guard ended, a stateless run or a replaced run. A failed call never fails the reply.
- **Requested secrets** — the agent only ever holds a `ref`. Store header secrets ENCRYPTED in `aiUserPreferences.mcpSecretHeaders` (bound to server name AND url), never in `mcpServers[].headers`; join only in `getMCPServersQuery`/`getMcpSecretHeadersQuery`; keep them out of `redactPreferences`.
- Spending a ref requires the turn STARTED by the owner (`startedBy` in `vToolRunConfig` and `ToolCtx`).
- Delete the ciphertext when a reply ends for good (not at a pause) and when a paused reply is abandoned, always through `discardPausedThreadSecrets`, which denies pending SECRET requests (`resolvedBy: "abandoned"`, `TOOL_REQUEST_ABANDONED`).
- Refuse an answer when the saved server's URL differs from the card's `expectedUrl`.
- **Generated titles** (`agent/thread-title.ts`) — a regenerate reads its prompt at run time: the earliest successful user prompt within the active path's last `DEFAULT_RECENT_MESSAGES` rows. `admitTitleRun` checks the thread and takes the charge in one transaction; the answer is held in a `title-answer` row (`recordTitleAnswer`) until the write settles, so a failed write is retried from it without a second call; settling, a refusal or a lock deletes it.
- A locked chat's prompt never reaches a title model: each request goes through `titleDispatchGateway`, which takes a `title-dispatch` claim in the same transaction as the lock check and holds it until answered; `enableThreadLock` refuses while one is held. Keep both sides if either changes.
- **Attached files of a locked chat** — `beginFileAttach` (`agent/files.ts`) runs on the CALLER's shard (`beginFileAttach` in `chat/http.ts`, for `/chat/start` and `/chat/edit`) before the thread's shard is entered. It checks the files with `gatedFileIdsOnCallerShard` AND takes a `file-attach` claim in one transaction, held until the attach is saved; `enableThreadLock` refuses while the caller holds one (`agent/file-attach-claim.ts`), so a lock cannot commit between the check and the owner-shard read. A collaborator's passcode rows and file links live only on the collaborator's shard, so a check made only on the owner's shard lets their locked file into the owner's chat. Never make that check on the thread's shard alone. The destination's lock waits for the save too: `claimThreadAttach` (`agent/file-attach-thread.ts`) takes a claim on the THREAD's shard in the same transaction as its access check, and `enableThreadLock` refuses while one is held. A resend of a saved send (`peekChatStart`) checks and reads no files again; a message attaches at most `MAX_ATTACHED_FILES`.
- **Pinned goal** (`threads.pinnedGoal`, `goals/functions.ts`, owner-only set/clear) is stored, not applied here: the web app sends it as `goal` on each text send with no goal armed (`send-message.ts`). A send from another client carries no pin, so the pin is web-only until the server applies it. An explicit goal from an impersonating session is refused (403, `http.ts`); the web app withholds the pin while impersonating.
- **Pins** (`chat/pins/functions.ts`) — `createPin` takes message and image pins only. A document pin (a visual or plan: kinds in `chat/pins/pinnable.ts`) goes through `createDocumentPin`, which reads the document's title and message itself, refuses a document of another chat or one still streaming, and returns the existing pin for that document (`by_user_and_document`), so a document is pinned once per person.
